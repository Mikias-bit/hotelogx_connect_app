# Maintenance assignments

Maintenance Dashboard, Issues, Tasks and Assignments read the hotel's saved Issue,
Maintenance Task and MaintenanceWorker records from `/api/maintenance-operations`.
The pages no longer use the prototype technician names or generated briefing claims.
Errors are shown explicitly; an unavailable backend is not reported as an empty,
healthy hotel. Existing records in the database are preserved.

## Workflow

1. Create issues and follow-up tasks, or use existing records generated by guest
   conversations. Open **Maintenance → Assignments**.
2. Under **Technicians & WhatsApp settings**, register a technician's name and
   international WhatsApp number; enable the technician and WhatsApp tasks.
3. Select work and a technician, then **Assign & Send WhatsApp**. Assignment is
   `Assigned`, not `Accepted`. Names and assignment/acceptance/start/completion
   timestamps appear on the assignments page.
4. The technician messages `MAINTENANCE` to the hotel's connected internal number
   and sees the assigned locations and tasks, with **Accept**. The initial preview
   contains up to eight tasks; work is presented individually after acceptance.
5. **Accept → Start → Completed** updates the original Issue/Task, records an audit
   event attributed to the technician, and sends the next available task.
6. **Problem → Parts required / Need help** records a waiting/escalated status.
   The next text reply becomes a problem note. `MAINTENANCE` returns to current work.

`TASKS` also works for technicians registered only in maintenance. If a phone is
registered for both maintenance and housekeeping, use `MAINTENANCE` or
`HOUSEKEEPING` explicitly; signed buttons route to their department.

The UI refreshes on hotel-scoped SSE events, focus, and a 60-second polling backup.
Provider submission is not proof of delivery or acceptance. Ambiguous sends are
recorded as uncertain and are not automatically retried. Workers can request the
current work again. Duplicate webhook IDs and repeated assignment request IDs do
not reapply work or resend an assignment.

## Template

Configure an approved text-only template, for example `maintenance_assignment`,
with two positional body variables (worker name and number of tasks):

> Hi {{1}}, you have been assigned {{2}} maintenance tasks. Reply MAINTENANCE to view and accept your assignments.

Store the approved name and matching language (e.g. `en_US`) on the assignments
page. A recent inbound message permits interactive assignment messages; otherwise
the template is used. Without either, assignment is saved with `waiting_window`.
There is no fallback to a different hotel's WhatsApp credentials.

## Access and completion

Manager and Maintenance roles can manage workers/assignments. The existing
Maintenance role is treated as the maintenance coordinator, matching the current
Housekeeping role model. Technicians can work entirely through WhatsApp.

Every selection, action and update is checked against the authenticated hotel,
current worker and assignment. Signed worker buttons expire and are tied to the
worker's phone; reassignment or phone changes invalidate old actions. Version checks
reject stale selections and updates. Free-text staff names cannot assign work.

Completing one issue does not complete other maintenance tasks for the same room,
release/block a PMS room, or automatically tell a guest that a repair is fixed.
Room readiness and any guest communication remain separate staff decisions.
Housekeeping maintenance reports now create linked tickets. Repair completion
creates a housekeeping follow-up; inspection and Front Office release remain
separate. See [Room readiness and linked repairs](room-readiness-and-repairs.md).

## Deployment and validation

Apply `20261030010000_maintenance_assignments` before deploying the backend:

```powershell
npm.cmd run prisma:deploy
if ($LASTEXITCODE -ne 0) { throw 'Migration failed' }
npm.cmd run prisma:generate
if ($LASTEXITCODE -ne 0) { throw 'Client generation failed' }
gcloud.cmd builds submit . --config=cloudbuild.yaml --project=hotelogx
```

Push the frontend to trigger Netlify separately. No PMS MCP server change is needed.

Tests:

```powershell
node --test src/tests/maintenanceOperations.test.js
node scripts/test-maintenance-database.mjs .env
```

The database harness creates a disposable schema in the designated Neon test-data
database, applies migrations, and checks the lifecycle with mocked WhatsApp delivery.
It removes only that generated schema afterwards. A real technician/Meta test is
still required after deployment.
